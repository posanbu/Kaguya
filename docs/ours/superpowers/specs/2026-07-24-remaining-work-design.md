# Kaguya 人工待实现文档设计

## 目标

新增 `docs/remaining-work.md`，说明 Kaguya 在 3.1 init commit 之后，还需要哪些人工决策和工程实现，供项目负责人排期，也供开发者直接拆分任务。

本文档不把现有 demo 描述成生产实现，也不把已经完成的基础设施重新列为待办。

## 读者

- 项目负责人：需要了解阶段目标、优先级、依赖关系和推荐角色。
- 开发者：需要了解当前代码基础、具体交付物、代码落点和验收标准。

## 组织方式

采用“阶段路线图 + 子系统任务卡”的混合结构。

### 第一层：阶段路线图

- P0：跑通真实平台的最小生产闭环。
- P1：达到可维护、可恢复和可评估。
- P2：扩展平台、模态、插件、权限和规模。

每个阶段说明目标、进入条件、完成标志和内部依赖。优先级表达实施顺序，不给出未经团队评估的工期承诺。

### 第二层：子系统任务卡

每张任务卡统一包含：

1. 当前代码基础；
2. 为什么需要人工参与；
3. 需要作出的产品或技术决策；
4. 具体交付物；
5. 依赖关系；
6. 推荐负责角色；
7. 可验证的验收标准。

任务卡覆盖平台适配、真实 LLM、业务 Prompt、持久化、调度与部署、可靠事件处理、可观测性、评估、memory、管理界面，以及后续扩展能力。

## 内容边界

### P0：真实平台最小闭环

- 入站平台适配器、统一事件转换和出站消息发送；
- 真实 LLM provider、模型选择、密钥、配额、超时和限流；
- 人格、路由、回复、状态和 memory Prompt 的人工制定与审阅；
- 生产数据库选型、迁移、备份、数据保留和敏感信息策略；
- 常驻 scheduler、进程生命周期、部署配置和环境隔离。

P0 的完成标志是：真实平台消息可以进入统一事件边界，经过真实模型和生产存储后可靠发回平台，并能运行心跳和记忆任务。

### P1：可维护与可恢复

- 持久化事件队列、幂等、重试、死信和崩溃恢复；
- 日志、指标、trace、告警和运维手册；
- Promptfoo 真实数据集、质量阈值和发布门禁；
- memory 检索、排序、压缩、淘汰和供应商/实现选择；
- 管理 API/UI、运行状态查看和安全操作入口。

P1 的完成标志是：关键失败可检测、可重试、可恢复，Prompt 或模型变更具有可重复的回归依据。

### P2：扩展能力

- 更多消息平台与媒体类型；
- 插件、工具和外部能力接入；
- 用户权限、租户隔离和审计；
- 多实例调度、分布式一致性和水平扩展。

P2 只描述扩展方向和进入条件，不提前固定尚未发生的产品需求。

## 人工决策与编码工作的区分

文档会明确标记两种工作：

- `人工决策`：需要产品、安全、运维或领域判断，例如保留策略、Prompt 语气、模型成本和平台权限。
- `工程实现`：决策确定后可以编码和测试的工作，例如 adapter、repository、queue consumer 和 metrics exporter。

不能在缺少人工决策时用默认值假装生产方案已经确定。

## 与当前代码的关系

任务卡会引用现有包和入口：

- `@kaguya/schema`、`@kaguya/sdk`：共享事件和声明契约；
- `@kaguya/engine`：进程内事件与工作流执行；
- `@kaguya/scheduler`：触发器原语；
- `@kaguya/prompt`：Prompt 编译与 provenance；
- `@kaguya/llm`：统一模型边界与 trace；
- `@kaguya/database`：当前 SQLite 实现；
- `apps/demo`：composition root 和确定性示例。

文档末尾会列出不需要重做的基础设施，避免后续开发绕开已建立的事件校验、生命周期、Prompt provenance 和 LLM 输出校验。

## 可执行检查表

最后附一份适合转成 GitHub issue 的检查表。每个条目保持单一交付目标，并引用对应任务卡；检查表不以“接入生产”“完善功能”等模糊表述作为完成标准。

## 文档验收

- 覆盖 P0、P1、P2，且阶段依赖没有倒置；
- 每项 P0/P1 工作都有当前基础、人工决策、交付物和验收标准；
- 当前 demo 能力与生产能力明确分开；
- 不包含工期承诺、真实密钥或未经团队决定的供应商结论；
- 与 `README.md`、`docs/architecture.md` 和 `CONTRIBUTING.md` 的现状描述一致；
- Markdown 格式检查通过。
