# Global Profile Registry Design

**Status:** Approved

**Date:** 2026-08-30

**Issue:** [#45](https://github.com/posanbu/Kaguya/issues/45)

## Why the Profile contract must change

Kaguya currently treats a Profile as both a persisted configuration document
and an implicit fallback. Initialization creates a runnable Profile, the
Registry names one `defaultProfileId`, `resolveProfileById()` accepts an omitted
ID, modules may override the Profile in their own settings, and the Server may
choose the default when no module choice exists. The setup UI reinforces this
ambiguity by pre-filling a Profile name without providing Profile management.

Issue #37 has already removed Session bindings from the configuration index.
This design completes the separation: a Profile becomes a globally selected,
explicit startup configuration. The Registry owns exactly one
`selectedProfileId`; the Server resolves that ID once at startup; every module
uses the resulting frozen runtime context.

## Goals

- Reserve the Profile ID and name `default` and guarantee that this Profile is
  always present.
- Bootstrap a new configuration root with an empty `default` Profile and no
  fabricated provider, model, platform, or plugin values.
- Make `selectedProfileId` the only runtime Profile selection.
- Require explicit IDs for all Profile reads and writes.
- Provide authenticated Profile creation, replacement, selection, and deletion
  APIs, plus safe anonymous setup status.
- Let WebUI users create, inspect, edit, and select Profiles without clearing
  fields the current form does not display.
- Freeze the selected Profile for the lifetime of a Runtime process and require
  a restart after selection or relevant configuration changes.
- Reject index versions 1 and 2 without migration or file modification.

## Non-goals

- This change does not add hot Runtime reconfiguration.
- It does not add Profile selection to messages, information atoms, platform
  metadata, module settings, selectors, memory, or any other request context.
- It does not migrate legacy indexes or preserve compatibility aliases for
  `defaultProfileId`, module `profileId`, or the old setup write endpoint.
- It does not introduce provider fallback, model fallback, remote model probing,
  or automatic Profile selection.
- It does not implement the one-time Gateway Token lifecycle proposed by #44.

## Registry invariants and persisted format

The index document advances to version 3:

```ts
interface UserConfigIndex {
  version: 3;
  selectedProfileId: ProfileId;
  profiles: UserConfigProfileMetadata[];
}

type ProfileId = "default" | UUID;
```

The Profile document remains version 1 because its settings representation does
not change. Its ID schema changes to the same `ProfileId` union used by index
metadata.

The schema and manager jointly enforce these invariants:

- `profiles` contains exactly one entry whose ID is `default`.
- The `default` metadata name and Profile document name are both exactly
  `default`.
- `selectedProfileId` references an entry in `profiles`.
- User-created Profile IDs are UUIDs generated by `randomUUID()`.
- Profile names are trimmed, non-empty, and unique across the Registry.
- Metadata IDs are unique.
- A Profile document ID matches its filename and metadata entry.

`default` is a reserved identifier, not fallback behavior. Calling an operation
with an unknown ID fails even when `default` exists. The manager never selects a
Profile by name.

## Explicit bootstrap and filesystem safety

`FileUserConfigManager.inspect({ rootDir })` remains read-only. It must not
create the root directory, `profiles/`, `index.json`, or a Profile file.

The new explicit operation is:

```ts
FileUserConfigManager.bootstrap({
  rootDir,
}): Promise<FileUserConfigManager>;
```

Bootstrap accepts only an absent or empty configuration root. A root containing
an index, an orphaned Profile, or any unrelated entry is not considered empty
and is rejected rather than overwritten. Bootstrap performs these steps:

1. Validate that every derived path stays inside `rootDir`.
2. Confirm the root is absent or empty.
3. Create the root and `profiles/` with sensitive directory permissions.
4. Write an empty `profile_default.json` using the existing atomic sensitive
   JSON writer.
5. Re-check that `index.json` is absent and publish the v3 index last.
6. Remove the newly written Profile if index publication fails.

Publishing the index last makes the Registry visible only after its referenced
Profile exists. Existing atomic rename, permission, symlink, and path-containment
protections remain mandatory. The manager write queue continues to serialize
mutating operations within one manager instance.

Server startup calls bootstrap explicitly only after a read-only inspection has
reported a genuinely empty configuration root. This is the sole automatic
caller: `inspect()` itself never writes.

## Configuration manager API

The public manager surface becomes explicit:

```ts
class FileUserConfigManager {
  static inspect(
    options: FileUserConfigManagerOptions,
  ): Promise<ConfigurationReadiness>;
  static bootstrap(
    options: FileUserConfigManagerOptions,
  ): Promise<FileUserConfigManager>;
  static open(
    options: FileUserConfigManagerOptions,
  ): Promise<FileUserConfigManager>;

  listProfiles(): readonly UserConfigProfileMetadata[];
  getSelectedProfileId(): ProfileId;
  getProfile(profileId: ProfileId): Promise<UserConfigProfile>;
  inspectProfile(profileId: ProfileId): Promise<ProfileReadiness>;
  createProfile(name: string): Promise<UserConfigProfile>;
  replaceProfile(
    profileId: ProfileId,
    replacement: ReplaceUserConfigProfileInput,
  ): Promise<UserConfigProfile>;
  selectProfile(profileId: ProfileId): Promise<void>;
  deleteProfile(profileId: ProfileId): Promise<void>;
  resolveProfileById(profileId: ProfileId): Promise<UserConfigProfile>;
}
```

`createProfile()` always creates empty settings and does not select the new
Profile. `replaceProfile()` replaces the complete Profile settings and review
acknowledgements; it never performs a server-side partial merge. It rejects a
name change for `default` and rejects duplicate names. Warning
acknowledgements must refer to warnings derived from the replacement document.

`selectProfile()` changes only `selectedProfileId`. It accepts an incomplete
Profile because the user may explicitly choose it and then finish configuring
it; readiness will keep Runtime paused until it is ready.

`deleteProfile()` rejects `default` and the currently selected Profile. Any
other known Profile may be deleted. `resolveProfileById()` requires an ID at the
type and runtime boundaries and returns only a ready Profile; it never falls
back to `selectedProfileId` or `default`.

## Readiness and Server startup

Configuration readiness is derived only from the selected Profile. The safe
Registry inspection result contains Profile metadata, `selectedProfileId`, and
the selected Profile's issues or warnings. It contains no Profile body, API key,
credentials, provider settings, platform settings, plugin settings, or raw
validation causes.

Startup follows one deterministic path:

1. Inspect the configuration root without writing.
2. Bootstrap only if the root is absent or empty.
3. Open the v3 Registry and read `selectedProfileId`.
4. Inspect and resolve exactly that Profile.
5. If it is invalid or requires review, start HTTP/WebUI setup mode while
   leaving Runtime, database business flows, and NapCat paused.
6. If it is ready, build one frozen global Profile runtime context and start the
   Runtime and adapters.

An incomplete unselected Profile does not affect startup. A missing selected
Profile, mismatched Profile document, unsafe path, unsupported index version, or
corrupt store is not recoverable setup state and fails closed.

## Runtime and module SDK

`ModuleModelSelection` contains only the model tier:

```ts
interface ModuleModelSelection {
  readonly modelTier: ModelTier;
}
```

The LLM reply module settings schema removes `profileId`. All module activation
settings and tests are updated accordingly. The Server loads only the selected
Profile and creates provider clients from that frozen document. The runtime
resolver maps a requested tier to the selected Profile's exact provider and
model; it does not hold a map of all Profiles and cannot honor an override.

Unknown tiers, missing targets, disabled or missing providers, unsupported
provider types, and missing credentials fail directly. There is no retry against
another Profile, provider, or model. The selected Profile ID may appear in
operational error text or provider client names, but it is never persisted in
messages or used as an aggregation key.

## HTTP management API

The existing anonymous `GET /api/v1/setup` remains the WebUI entry probe. Its
response includes safe Registry state:

```ts
interface SetupStatusResponse {
  status: "invalid" | "review_required" | "ready" | "restart_required";
  profiles: readonly UserConfigProfileMetadata[];
  selectedProfileId: ProfileId;
  issues?: readonly ConfigurationIssue[];
  warnings?: readonly ConfigurationWarning[];
}
```

The old `POST /api/v1/setup` is removed because it implicitly created or
modified a default Profile and combined creation, update, warning confirmation,
and selection.

The authenticated management API provides these operations:

- `GET /api/v1/profiles` returns metadata and `selectedProfileId`.
- `POST /api/v1/profiles` accepts `{ name }` and creates an empty unselected
  Profile.
- `GET /api/v1/profiles/:profileId` returns the complete secret-bearing Profile.
- `PUT /api/v1/profiles/:profileId` accepts the complete replacement body.
- `PUT /api/v1/profiles/selection` accepts `{ selectedProfileId }`.
- `DELETE /api/v1/profiles/:profileId` deletes an allowed Profile.

All six routes require the existing Gateway Bearer management credential. The
route declaration for `/profiles/selection` precedes the parameter route so the
literal path cannot be interpreted as a Profile ID. CORS allows `PUT` and
`DELETE` in addition to the existing methods.

Successful mutations report whether Runtime restart is relevant. Creating or
editing an unselected Profile does not alter the running context. Selecting a
Profile always requires restart for a running Runtime. Replacing the selected
Profile requires restart before the new contents can be used; the WebUI presents
the restart action only once the selected Profile is ready.

## WebUI workflow

Setup mode becomes a Profile management screen rather than a one-shot form. It
shows all Profile metadata and clearly marks `selectedProfileId`.

The user can perform three independent actions:

- Create a named Profile. The UI adds it to the list but does not select it.
- Save edits for the Profile whose ID is currently open.
- Select the open Profile globally.

Opening an editor requires an authenticated
`GET /api/v1/profiles/:profileId`. The client retains the complete returned
document. The current form edits its supported OpenAI-compatible provider and
model fields, then merges those changes into the retained document before
sending a complete PUT. This preserves undisplayed platforms, plugins,
credentials, provider extension settings, and review data unless the user has
explicitly changed the related visible control.

The editor never constructs a blank Profile as an update payload. A failed or
unauthenticated load disables saving. The `default` name is fixed in the UI, and
delete controls are absent or disabled for `default` and the selected Profile.
API enforcement remains authoritative even when the UI disables an action.

After the selected Profile becomes ready, or after selection changes to a ready
Profile, the UI displays a restart-required state. The browser does not request
hot Runtime reconfiguration.

## Error semantics

The configuration package keeps stable typed errors and adds an explicit legacy
version error where necessary.

- Malformed inputs and invalid Profile ID syntax map to HTTP 400.
- A syntactically valid but unknown Profile ID maps to HTTP 404.
- Duplicate names, attempts to rename or delete `default`, and attempts to
  delete the selected Profile map to HTTP 409.
- Missing or invalid management credentials map to HTTP 401 before parsing a
  secret-bearing request body.
- Unsupported v1/v2 indexes report that the operator must back up the
  configuration and reinitialize it. They are never rewritten or deleted.
- Corrupt stores, missing referenced files, permission failures, unsafe paths,
  and rollback failures remain fail-closed infrastructure errors.

Error payloads and logs may include a validated Profile ID or protected path
when useful, but never serialize Profile bodies, keys, credentials, settings,
or submitted secrets.

## Test strategy

Implementation follows strict red-green-refactor cycles. Tests exercise real
filesystem and Fastify behavior whenever practical.

Configuration model tests cover the reserved `default` ID, UUID-only user IDs,
required default metadata, exact default name, unique IDs and names, and
referential integrity for `selectedProfileId`.

Manager tests cover read-only inspection, empty bootstrap, refusal to bootstrap
a non-empty root, rollback on index publication failure, explicit unknown-ID
failures, empty unselected creation, full replacement, default protection,
explicit selection, selected deletion protection, readiness of only the selected
Profile, and rejection of v1/v2 indexes with byte-for-byte unchanged files.

Server tests cover bootstrap composition, setup mode, safe anonymous status,
authentication on every management route, HTTP status mapping, separate create,
replace, and selection calls, frozen selected Profile resolution, and the fact
that an incomplete unselected Profile does not block Runtime startup.

Module and Runtime tests prove that `profileId` is rejected by module settings,
that model selection carries only a tier, and that multiple modules resolve
through the same frozen selected Profile.

WebUI API and component tests cover metadata display, authenticated Profile
loading, create-without-select, explicit selection, default controls, preserved
hidden fields on replacement, failure states, and restart messaging.

Final verification runs:

```text
pnpm build
pnpm lint
pnpm typecheck
pnpm test
pnpm format:check
git diff --check
```
