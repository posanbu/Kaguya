# 测试与兼容边界

这页区分用户可以依赖的行为、开发者用来实现行为的机制，以及仍待清理的历史代码。测试应保护可观察的结果和持久化保证；一个旧实现曾经存在，不自动成为需要永久维护的产品接口。

## 产品边界

**配置** — 用户按[配置概览](../guide/configuration)创建当前 Registry、Profile 和模块实例。保存、选择与显式应用是不同操作；保存成功不表示运行实例已切换。当前格式以配置 schema 和公开管理接口为准。旧字段、旧实例目录与旧版本文件不属于受支持格式；不承诺自动转换，也不以识别每一种历史格式作为产品能力。

**数据库** — 生产使用 PostgreSQL 17。空的专用 schema 可以初始化；已有 schema 必须能安全承载当前账本与模块数据。不兼容结构在启动阶段报告错误，不能等到处理消息时才暴露，也不能删除或覆盖用户数据。数据导入、跨格式迁移与回退需要独立设计，不由普通启动或测试夹带完成。

**运行结果** — 同一消息或任务的重放不能产生重复业务终态；授权在最终发送时仍须有效；重启、租约过期及失败恢复应留下可追溯的事实。这些是产品行为，不能为了缩短测试而只验证返回对象的形状。

## 开发与测试责任

**Schema 与纯逻辑测试** — 验证当前字段、动作、范围、原因映射和输出约束。相同规则的数值、枚举或目标类型变体优先在此层逐一验证，不为每个变体重新创建 Runtime 和数据库。

**配置与数据库组件测试** — 配置测试使用临时目录验证当前格式读写、无效内容的失败关闭、文件不变和凭据脱敏。PGlite 测试验证真实 SQL 事务、投影、回放和约束；每例需要独立状态时保持隔离。真实 PostgreSQL 套件验证跨连接竞态、数据库语义和与 PGlite 共用的账本契约。

**完整链路测试** — Server、Runtime、Light 和投递测试各保留能证明跨模块装配的代表场景。重启、取消、持久化恢复、授权撤销及发送时竞态属于不同失败窗口，应分别验证。重复的输入变体可以下沉；不把多个独立失败窗口合成一条难以定位的长用例。

**PR 关键测试** — 每个 PR 并行跑文档检查、lint/typecheck、四个 Ubuntu 关键测试分片，以及 Ubuntu 上的全部消息路由与授权用例。三平台覆盖由每日完整测试提供。关键清单在根目录 `vitest.critical.config.ts`，覆盖配置、启动、数据库幂等与恢复、模型任务持久化、授权、Web 对话和发送规划。`pnpm test:critical` 执行清单内文件的全部用例。关键分片和路由作业在测试后检查 JSON 报告，要求所有用例通过且零跳过、零待办。关键分片提供真实 PostgreSQL 服务，执行模型任务的两种数据库后端用例。清单文件缺失或 CI 缺少测试数据库地址会直接失败，不能静默减少覆盖。修改关键行为时同步维护清单。

**耗时与维护** — CI 工作流不设置自定义作业硬超时，GitHub 平台默认限制仍然适用。PR 关键测试以每个作业约 3 分钟为维护目标，包含安装、构建和测试。测试作业只构建 Server 及其依赖，完整类型检查仍由独立作业执行。关键测试必须全部完成，不因超过目标耗时而跳过用例、提前停止或返回成功。定期检查安装、构建和测试文件耗时，精简配置或重新分配分片后重跑全部关键测试，不减少关键覆盖。排队、runner 状态及独立的 NapCat、离线基准工作流仍会影响等待时间。审计同时看作业关键路径、runner 总耗时和测试文件耗时，不能把累计 worker 时间当作 PR 等待时间。

**每日全量** — 每天北京时间 08:00 在默认分支触发 Ubuntu、macOS、Windows 的两个完整 Vitest 分片、真实 PostgreSQL 套件，以及两个离线基准工作流。也可分别手动触发这些工作流。定时触发可能延迟，见 [GitHub 定时事件说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。影响数据库并发、持久化或跨系统行为的变更可在合并前手动跑全量。全量测试失败应修复，关键测试通过不表示全量测试已通过。

## 当前实现与后续方向

当前配置读取仍对某些旧 Profile 或 reply 模块给出专用错误。数据库启动仍会调整旧 Web Memory 约束，并在缺少 lifecycle 投影时从现有账本回填。这些是**现有代码事实**，本轮不移除，现有测试也继续覆盖实际执行的数据库路径；它们不构成对其他旧格式的兼容承诺。

后续若决定只验证完整的当前结构，应在独立代码变更中移除上述专用分支与自动调整，同时补齐当前数据库约束和投影的启动校验，并同步替换相应测试。配置变更请求与运行状态隔离由[研究 issue #257](https://github.com/posanbu/Kaguya/issues/257)单独跟踪，不由测试整理改变热应用行为。
