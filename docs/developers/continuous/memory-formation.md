# 经历与长期认识

本文回应 [#242](https://github.com/posanbu/Kaguya/issues/242)，复用[情境与观察](./observation)的 scene、冻结输入和恢复规则。以下是待实现的形成契约，既有 Memory 配置与行为仍见[Memory 认知层](../memory)。

## 四层职责

**Raw evidence** — 保存原始消息、原生回复关系、人物标识、时间及 agent 的行动和结果。触发单位可以是一条 Information；真实输入就是对应原始事实。沿用来源 Information ID 及写回操作身份去重，更正追加为新证据。并非所有事件都必须复制进当前文本 Memory 表；已有账本事实可以通过引用参与形成。

**Context / observation** — 为一次具体职责冻结完整可见范围，包括新证据、必要历史和既有经历版本。触发可以是合并后的 tick、积压、空闲或显式 flush；语义输入是冻结清单，不是触发 atom。观察成功按该消费者职责推进进度，Memory 尚未发布时任务仍保持待形成状态。

**Experience / episode** — 表达谁在什么场景经历了什么、旁支是什么、后来如何更正及哪些部分仍不确定。一次 observation 可更新多段经历，多次 observation 也可参与同一经历。形成器以持久操作 ID、目标经历 ID 和预期版本提交；正文提供可理解的经历，结构化元数据保留参与者、来源、边界、时间和修正关系。来源列表不能替代正文，也不能单独证明每条结论归属正确。

**Long-term cognition** — 从经历和直接证据提炼人物、关系、自我或表达认识。触发单位是待巩固的证据/经历版本集合；语义输入包括被修订的旧认识及其依据。每条认识保留主体、陈述者、scope、有效时间、支持和反对来源、不确定性与形成版本。只在有明确证据和范围规则时跨 scene 提升，不能把一次玩笑、转述或短期状态直接写成全局永久偏好。

层级允许有理由的旁路：显式用户更正可以直接修订相关认识，但必须记录来源和被修订目标；Identity 仍可逐条正规化，Expression 可继续按多来源 batch 学习。所有派生层遵守相同的来源与修订边界，不要求只有一条固定流水线。

## 如何形成一段经历

第一版采用“场景内增量形成、允许修订”的协议：形成器读取新的 observation 和当前相关经历版本，提出新建、补充、修正、关联或保持不变的操作。原生 reply 关系、参与者、话题连续性和时间共同作为证据；群聊中的插话可以成为旁支，不强制按相邻消息合并。

封口表示暂时没有待纳入证据，不能表示永远不可更改。空闲、显式结束或预算上限可触发封口；晚到消息和更正可以重开同一经历并产生新版本。具体阈值及语义分段质量留给实现中的策略与样本评估，协议不依赖固定秒数或 32 条窗口。达到预算时分段并显式保留延续关系，不隐瞒截断。

新建经历先为形成操作持久分配目标身份；重试不得重新分配另一经历 ID。合并和拆分保留原经历版本及显式关系，读路径按已发布版本解析当前归属，不能物理删除旧经历来隐藏错误。模型提出操作，服务端校验引用可见性、身份归属、预期版本和操作范围后才提交。

## 幂等、并发与修正

形成请求固定 observation ID 集合、输入经历版本、策略/生成器版本和稳定操作 ID。LLM 请求结果在发布前持久保存；崩溃后可重试计算，但唯一提交约束保证同一操作只发布一次。协议不承诺模型恰好调用一次，也不把重复调用的文本必然一致作为恢复条件。

经历修订采用预期版本比较。两个任务同时编辑同一版本时只有一个提交成功；另一个任务基于新版本形成显式后继操作，不静默覆盖或复用已过期输出。派生版本、操作完成状态与形成进度应原子生效，或从唯一发布事实幂等恢复。被旧 observation 支持的历史版本仍可查询，但不能作为当前版本重新覆盖较新的更正。

撤回、更正和身份拆分使依赖产物进入待重算或失效状态。召回过滤已撤回或失效依据；Wiki、向量索引等异步投影落后时，读取端仍依据权威版本/撤回状态过滤，不等索引刷新才生效。回滚采用新修订引用旧内容并记录原因，不倒退账本或覆盖历史版本。

人物认识的更正必须验证陈述者和主体关系。B 对自己的澄清可以修订 B 的相关自述；C 对 B 的猜测形成另一条带归属的认识，不能自动撤销 B 的陈述。同名和换昵称由既有 Identity 契约处理，形成器不创建第二套人物身份。

## 未完成时如何召回

默认读取最近成功发布且仍有效的经历版本，同时保留当前未纳入的原始证据和后台滞后状态。没有旧版时可以仅返回原始证据，不把缺少派生记录解释成“没有发生过”。知识查询应允许按来源和时间回看，避免只检索文字摘要。

在线 observation 冻结精确版本及双时间边界：只使用截至该次读取已知且符合事件时间约束的证据；后来修订不会偷偷进入旧 Planner 的重放。新 observation 可以看到新版本。回放评估需要同样约束原文、派生版本与索引命中，防止后来的更正泄漏进旧时点。

后台失败保留旧有效版本、错误和待形成范围，按有界策略重试；重试耗尽转为可见失败，不把空结果当成新的领域事实。成功的“没有值得形成的变化”也须保存已检查范围和保持不变的决定，以免重复处理，但不生成虚假的经历正文。

## 当前模块的保留和迁移

**Writeback 保留** — 当前逐条保存 inbound 是原始证据入口。逐消息写回完成可以更新后台待处理范围，但不再要求每条完成都立刻发起新的重叠认知请求。

**32 条 cognition 窗口调整** — 当前 [`memory-cognition`](https://github.com/posanbu/Kaguya/blob/ff5544603f528601b7a8930cf0396199691de4c2/packages/modules/src/first-party/memory-cognition/index.ts)已冻结同场景来源，#245 还补充了平台消息 ID 和 replyTo；它仍是有界窗口，不是完整经历。迁移先增加独立范围/任务和版本契约，再适配 provider。旧 `core.memory.text` 标为旧窗口来源，禁止直接赋予完整经历身份；必要的历史重建单独执行并记录生成器版本。

**Knowledge 分层保留** — event、claim、episode 可以提供存储与检索基础，但当前消息到 event 的投影不证明已完成跨消息经历形成。后续需检查现有 episode 能否表达版本、重开、合并/拆分和逐条结论来源，再决定增量扩展或新投影；不先复制出一套互不关联的 Knowledge。

**Expression batch 保留** — 多来源批次符合其职责，仍需记录批次身份、来源截止点与派生项。Expression 的学习进度不能冒充整个 scene 的 Memory 形成进度；来源更正和撤回需要传播到受影响产物。

Agent 的消息意图、实际投递、工具结果、TTS 合成和播放结果应分别进入经历可选证据，不能把“想说”写成“已经告诉对方”。新增非文本证据通过版本化输入适配，保留旧 provider 的能力边界。切换形成器须显式启用，避免新旧 writer 同时发布同类权威结果；回退保留所有新版本，恢复旧 writer 时仍应用撤回与范围过滤。

## 群聊验收与取舍

A 问 B 咖啡习惯，C 插话泡茶，B 回复「已经戒了」。第一版经历记录提问、答复与 C 的旁支，不能给 C 或 A 增加戒咖啡偏好。B 随后更正「晚上不喝，白天还喝」，新版本保留更正经过，旧“完全戒了”的解释退出当前有效认识。原生 reply 缺失时，归属应保留不确定性，不能只按最近发言者补齐。

把更正放在第 33 条之后，并分别在形成发布前、发布后和投影更新前重启。应证明更正仍被发现、同一操作只发布一个版本、旧版召回可审计且当前读取不会返回已失效结论。再加入旁观者相反陈述、两个 worker 同时修订、来源撤回、合并/拆分及后台长期失败，用来源和版本断言验证。

未采用“增大窗口即可获得经历”，因为容量不能定义语义归属与修正；未采用“直接更换 Mem0 为另一供应商”，因为调用方仍需确定场景、边界和生命周期；未采用“只保留 Wiki 文本”，因为可读页面不能替代原始来源及可修订认识。

实现与迁移跟踪在 [#248](https://github.com/posanbu/Kaguya/issues/248)；跨领域检视与完整时序验收见 [#250](https://github.com/posanbu/Kaguya/issues/250)。
